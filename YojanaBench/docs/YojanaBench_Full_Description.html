YojanaBench addresses this gap with two deliverables: (1) a human-verified benchmark of real scheme guideline PDFs with QA pairs, counterfactual/edge-case scenarios, and verdict references, and (2) a reproducible multi-agent audit pipeline (Corpus, Intake, RAG, Entitlement, Verification, Orchestrator, Evaluation, and Appeal agents) built on LangGraph + Ollama with zero API cost, evaluated using Exact Match, F1, verdict accuracy, entitlement error, and ablation studies.

1. Introduction & Background

1.1 Welfare-Scheme Landscape in India

The Government of India and state governments together run approximately 950+ welfare schemes covering food security (ration/PDS), old-age/widow/disability pensions, scholarships, employment guarantee (MGNREGA), housing (PMAY), farmer aid (PM-KISAN), health insurance (Ayushman Bharat), and beneficiary assistance programs. Each scheme is defined and operated through official guideline documents — typically long PDFs issued by the relevant ministry or department.

1.2 Role of Guideline Documents

These guideline PDFs are the legal and administrative source of truth for:

  • Eligibility criteria — age limits, income ceilings, category (SC/ST/OBC/General), residency, family income, landholding.
  • Entitlement formulas — exact benefit amounts: pension tiers, ration quantum per member, scholarship fee waivers, wage rates.
  • Document requirements — Aadhaar, income certificate, caste certificate, Ration card, bank passbook, domicile proof.
  • Application & appeal procedure — filing steps, timelines, revision/appeal hierarchy (Block → District → State Commission).

1.3 Real-World Failure Modes

FailureConsequence
Eligibility misreadingWrongly approved (leakage) or wrongly rejected (exclusion) applications
Wrong entitlement calculationIncorrect benefit amounts paid to crores of beneficiaries
Mis-routing of applicationsCases sent to wrong department/channel; months of delay
No quality test for AI systemsAny deployed AI tool is untested against a ground standard

1.4 Why Now

LLM-based assistants and RAG systems are being proposed for citizen-facing governance. Without a benchmark, there is no way to measure whether such a system reasons correctly over scheme rules. YojanaBench provides that measuring instrument — for our own pipeline and for any future research in this space.

2. Problem Statement

India runs ~950+ central/state welfare schemes (ration, pensions, scholarships, employment, beneficiary aid) governed by dense PDF guideline documents. Every year, eligibility errors, wrong entitlement calculation, and mis-routing of applications cause huge delays. Yet there is no structured benchmark to test whether AI agents can reason correctly over these real documents — existing benchmarks are English-general (GAIA) or Chinese-law (LawBench). Consequently:

  1. Researchers cannot compare document-reasoning methods on Indian welfare documents.
  2. Deployed AI tools cannot be validated for eligibility and entitlement correctness.
  3. Citizens bear the cost of errors in the form of rejected claims, wrong payments, and delayed appeals.

Project goal: build the missing benchmark (dataset + protocol) and a multi-agent audit pipeline that performs the full application-audit workflow — intake, retrieval, entitlement computation, verification, verdict, evaluation, and appeal routing — and demonstrate its correctness against the benchmark.

4. Objectives

  1. Shortlist and collect 10–15 high-volume scheme guideline PDFs (central + state; PDS, pensions, scholarships, employment, beneficiary aid).
  2. Build a structured scheme schema (eligibility clauses, entitlement formulas, document checklist, appeal hierarchy) per scheme.
  3. Create human-verified QA pairs across 4 categories: eligibility, entitlement, documents, appeal steps.
  4. Design counterfactual and edge-case scenarios (boundary incomes, missing documents, overlapping schemes) with ground-truth verdicts.
  5. Implement the multi-agent audit pipeline (Corpus, Intake, RAG, Entitlement, Verification, Orchestrator, Evaluation, Appeal agents).
  6. Define and run the evaluation protocol (EM, F1, verdict accuracy, entitlement error, confidence calibration).
  7. Run baselines and ablations (single-LLM vs multi-agent; agent-removal studies).
  8. Build a dashboard + demo scenarios showing approve / reject / appeal flows.
  9. Release the benchmark and pipeline with documentation, licenses, and statistics.

5. System Architecture

6. Detailed Agent Descriptions

6.1 Corpus Agent (Ingestion)

  • Input: scheme guideline PDF files (public government documents).
  • Functions: PDF text extraction (PyMuPDF/pdfplumber) → section-aware chunking (by clause/section headers, not fixed tokens) → schema extraction using LLM (eligibility clause, entitlement rule, document item, appeal step) → embedding into vector store with metadata (scheme_id, section type, page).
  • Output: vector store + structured SchemeSchema JSON per scheme.
  • Why special chunking: scheme rules are clause-structured; naive chunking splits a rule from its condition — section-aware chunking preserves rule integrity.

6.2 Case-Intake Agent

  • Input: a case application (form fields or unstructured text) + attached document list.
  • Functions: field extraction (age, income, category, region, family size) with validation; detect target scheme; identify the document checklist the case should have; flag missing submissions early.
  • Output: CaseRecord (structured fields + needed_documents vs submitted_documents diff).
  • Edge handling: ambiguous values (e.g., income in “lakhs” vs rupees) normalised; unknown fields marked, not guessed.

6.3 RAG Retrieval Agent

  • Input: CaseRecord + scheme_id.
  • Functions: hybrid retrieval (dense vector + keyword/BM25) over scheme chunks; re-ranking to top-k clauses; returns eligibility clauses relevant to the applicant's profile and entitlement rules for the scheme.
  • Output: evidence set: clause IDs + text + source pages.
  • Why it matters: verdicts must be grounded in retrieved clauses (explainability + citation), not model memory.

6.4 Entitlement-Calculator Agent

  • Input: evidence clauses + applicant fields.
  • Functions: convert retrieved benefit rules into executable computations (e.g., pension = tier(amount by age+category); ration = quantum per member × family size; scholarship = fee − waiver%). Applies conditions (income ceiling, BPL/APL status) and computes the exact benefit.
  • Output: computed_entitlement (amount/quantity) + the formula + clause IDs used.
  • Design rule: arithmetic is done by deterministic code where possible; LLM only maps rule → formula (reduces hallucinated math).

6.5 Verification Agent

  • Input: CaseRecord + retrieved clauses + computed entitlement.
  • Functions: (a) document completeness check against required checklist; (b) eligibility condition check (age/income/category/residency) per clause; (c) cross-check: re-derive eligibility independently from clauses and compare with Entitlement Agent's result (multi-agent disagreement forces “needs_info”).
  • Output: missing_documents[], ineligible_flags[], cross-check status (agree/disagree).

6.6 Orchestrator (+ Human-Approval Gate)

  • Framework: LangGraph state machine controlling agent order, retries, and conditional branches.
  • Functions: merges agent outputs into a final Verdict (decision + explanation + evidence + confidence); enforces a human-approval gate when confidence < threshold or when Verification reports disagreement.
  • Output: Verdict object; full agent trace stored for auditability.

6.7 Evaluation Agent

  • Input: Verdict + YojanaBench ground truth.
  • Functions: computes EM, token-F1, verdict accuracy, entitlement error (absolute/relative), confidence calibration; aggregates per scheme, per QA category; produces results tables/plots and ablation comparisons.
  • Output: ScoreReport (per item + aggregate).

6.8 Dispute / Appeal-Routing Agent

  • Input: rejection Verdict + scheme's appeal hierarchy.
  • Functions: determine correct appeal channel (e.g., Block Development Officer → District Magistrate → State Social Welfare Commission), generate draft appeal text citing the rejected clause, note deadlines.
  • Output: appeal routing instruction + draft appeal letter for human review.

CategoryQuestion TypeExample

7.3 Counterfactual & Edge Cases

  • Boundary values: income exactly at the ceiling (₹1.00 lakh vs ₹1,00,001); age exactly at cut-off (59 vs 60).
  • Missing documents: eligible on criteria but lacks one mandatory certificate → correct verdict is “needs_info,” not “eligible.”
  • Category swaps: same profile under SC vs General quota changes entitlement tier.
  • Overlapping schemes: applicant eligible for two benefits; benchmark expects correct identification.
  • Distractor schemes: question about scheme A answered using scheme B's rules → tests retrieval precision.
  • Negation/trick phrasing: “not exceeding,” “at least,” double negatives in clauses.

7.4 Ground Truth Format

{ "id": "YB-PDS-0042", "scheme_id": "PDS-APL-2023", "category": "entitlement" | "eligibility" | "documents" | "appeal", "question": "...", "reference_answer": "...", "verdict": "eligible" | "ineligible" | "needs_info", "entitlement_value": 5.0, "entitlement_unit": "kg/month", "evidence_clause_ids": ["PDS-APL-C12", "PDS-APL-C14"], "counterfactual_of": null, "edge_case": "boundary_income" | null, "annotator_agreement": true }

7.5 QA Production & Verification Process

  1. Authoring: team members draft QA pairs directly from scheme PDFs, citing page/clause.
  2. Independent check: second member verifies answer against the source clause.
  3. Adjudication: disagreements resolved jointly with the guide; only agreed items enter the benchmark.
  4. Agreement metric: report % inter-annotator agreement as a dataset-quality statistic.
  5. Counterfactual generation: each base QA item gets ≥1 perturbed variant with updated ground truth.

14. Feasibility & FYP Suitability

  • Zero API cost: Ollama + LangGraph + open-source vector store — fully reproducible on a normal laptop.
  • Data accessibility: all scheme PDFs are public; no private/government API access needed.
  • Strong examinability: dataset statistics, metric tables, ablation charts, live demo — ideal defence material.
  • Team fit: 3 students / 19 weeks with clear parallel workstreams (dataset / agents / evaluation-dashboard).
  • Clear two-deliverable structure: data contribution + systems contribution; both independently gradeable.

15. Possible Extensions & Future Work

  • Multilingual QA: questions/answers in Hindi + regional languages (tests cross-lingual document reasoning).
  • Scale the corpus: add schemes incrementally; measure benchmark growth effects.
  • Vision modality: handle scanned PDFs and application-form images (VLM + OCR).
  • Human study: compare agent verdicts with actual welfare-officer decisions.
  • Model comparison: benchmark across larger open models and closed APIs (optional, reported separately).
  • Deployment pathway: integrate with citizen-facing portals as a decision-support (not decision-making) tool with the human-approval gate.
